# Open-Source Integration Research — FANUC Conveyor Pick-and-Place in Isaac Lab 3.0 / RSL-RL

**Stack under research:** simulated conveyor pick-and-place, 6-axis arm (FANUC M-10iD/12 proxy), Isaac Lab 3.0.0 manager-based task, OvPhysX, kit-less, RSL-RL PPO (`rsl-rl-lib` 5.x), Kaggle T4 notebooks only (pip-installable, no system installs, no Isaac Sim GUI), scripted teacher (pure-Python FK + damped-least-squares IK) for demonstrations, BC warm-start. **Current blocker: pure PPO and BC warm-start both at 0% success; the warm-start appears destroyed at the BC→RL interface.** All facts below were read 2026-10-28; repo facts are from the projects' own GitHub pages, docs facts from official Isaac Lab / project documentation. Where Isaac Lab 3.0 / rsl-rl-lib 5.x compatibility could not be verified, it is said explicitly.

## Summary

1. **The BC→RL failure is the best-studied problem in this report, and the fix is a recipe, not a library.** No maintained, pip-installable project plugs DAPG / RLPD / IBRL into a custom Isaac Lab + RSL-RL PPO pipeline. The two reference repos are small, old-stack, and — in IBRL's case — **have no license file at all**. What transfers is a concrete, convergent recipe found independently in DAPG, IBRL's RFT baseline, FLaRe-style fine-tuning, and recent PPO+BC papers: keep a (decaying) BC/KL anchor loss *during* RL, warm the critic up on BC-policy rollouts before any actor update, set the entropy bonus to ~0 at the interface, freeze or separately parameterise the action std, use a much smaller actor LR, and gate the PPO term in over a warm-up (e.g. β(t)=tanh(t/T)). Reimplementing that inside the already-present RSL-RL PPO is a 3–5 day job and is Rank 1.
2. **Because the teacher is scripted and free to query, DAgger is unusually cheap here** — and RSL-RL already ships the machinery (Student-Teacher Distillation) plus Isaac Lab ships Mimic/MimicGen-style demo augmentation. You do not need a human-in-the-loop DAgger project.
3. **cuRobo is the highest-value external integration — with a version trap.** cuRobo **V1 is non-commercial (NVIDIA license)**; **V2 (v0.8.0, April 2026) is Apache-2.0** and a rewrite. Isaac Lab's own README still warns that the cuRobo its `isaaclab_mimic` extension requires "has proprietary licensing terms" — i.e. the in-tree path points at the old terms. Use V2 directly for the teacher/collector, not via the old pinned path, and budget for a source build on Kaggle.
4. **Do not switch RL libraries for speed.** Isaac Lab's own benchmark (RTX 4090, 65.5M steps): RL-Games 203 s, skrl 204 s, RSL-RL 207 s, **Stable-Baselines3 6,320 s (~30× slower)**. The only library worth a spike is **skrl**, not for speed but because it natively supports Isaac Lab *and* off-policy SAC/TD3 — the algorithm family RLPD/IBRL actually live in.
5. **Physics/rendering gains are already inside Isaac Lab 3.0** — the Newton (MuJoCo-Warp) backend with CUDA graphs and the OVRTX renderer — so the work is A/B spikes, not new dependencies. Caveat: Newton/Warp 1.18 wants driver R580+ (Turing CC 7.5 is the floor — a T4 is exactly CC 7.5); Kaggle's driver version was not verified, so OvPhysX may remain the safe default.
6. **For video, the single biggest new find is NVIDIA's SimReady Central Library** (launched 21 Oct 2026: 2,000+ free OpenUSD assets on Hugging Face, OEM partners **including FANUC**) — plus CC0 PBR materials from Poly Haven/ambientCG to convert to USD/MDL for OVRTX. Per-asset SimReady licensing was **not** verified; check before any commercial use.

## Findings

### 1. Imitation → RL done right

**What the named methods actually are, and what is reusable:**

| Method | Reference repo | Verified status | PPO-compatible? |
|---|---|---|---|
| DAPG | `aravindr93/mjrl` (official) — https://github.com/aravindr93/mjrl | 467★, Apache-2.0, 0 releases, Python 3.7 / mujoco-py era code | Yes in spirit: DAPG = BC pre-train + policy-gradient fine-tune with an augmented gradient / BC term on demo data that decays. Code is not runnable in this stack; the *loss* is ~30 lines. |
| RLPD | `ikostrikov/rlpd` — https://github.com/ikostrikov/rlpd | 420★, MIT, 0 releases, JAX, built for D4RL/Adroit, Python 3.9 conda | **No.** RLPD is off-policy SAC-style: symmetric sampling (50% demo / 50% online per batch), LayerNorm critic, critic ensemble. Nothing in it attaches to on-policy PPO. Its *principles* (never stop feeding demos; normalise the critic) transfer only if you move to SAC. |
| IBRL (+ RLPD + RFT baselines in same repo) | `hengyuan-hu/ibrl` — https://github.com/hengyuan-hu/ibrl | 80★, 9 commits, 0 releases, **⚠️ NO LICENSE FILE in the repo root — treat as all-rights-reserved: study the algorithm, do not copy code**. Requires MuJoCo 2.1 binary install, a compiled C++ module, conda Python 3.9 — **not Kaggle-compatible as-is** | **No, not directly.** IBRL is TD3-based: a frozen BC policy proposes actions, a Q-ensemble picks argmax(Q) between BC and RL actions both for acting and for bootstrap targets. The portable idea for PPO: *keep the BC policy alive as a separate actor and let a value function arbitrate*, instead of overwriting one set of weights. |
| FLaRe | Paper/project page only (Hu et al., ICRA 2025, robot-flare.github.io) | Large-scale RL fine-tuning of BC generalist (VLA-scale) policies: robust pre-trained representations + large-scale training + **gradient stabilization**; +23.6 pts sim / +30.7 real over prior SOTA with sparse rewards only | Pattern only. **No maintained repo suitable for a small MLP PPO policy was found/verified.** Do not plan an integration; borrow the stabilisation ideas. |
| DAgger-in-simulation | No external project needed | Teacher is scripted ⇒ expert queries on student-visited states are free and deterministic | Yes — see below. |

**The convergent BC→RL interface recipe (this is the actionable output of Axis 1).** Independent sources agree on the same failure causes named in the mission — random critic, entropy bonus, exploration noise:

- **Anchor the actor during RL, decay the anchor.** DAPG keeps a demonstration gradient term that decays over training; RFT (regularized fine-tuning, shipped as a baseline inside the IBRL repo) does the same for TD3. For PPO this becomes `L = L_PPO + λ_BC(t)·MSE(π(s_demo), a_demo)` with λ decaying, or equivalently a KL penalty to a **frozen copy** of the BC policy. A recent excavation-policy fine-tuning work (ExT, summarised from the paper) uses exactly: KL-to-frozen-pretrained-policy with **β = 0.02**, entropy coefficient **0.0005**, actor LR **1e-5**.
- **Warm up the critic before touching the actor.** ExT warm-starts a separate critic from rollouts of the pre-trained policy for 100 steps. A 2025 action-chunked PPO + self-BC paper (arXiv:2509.25718) makes the same point formally: its objective is `L = β_t·L_PPO + L_BC` with **β_t = tanh(t / T_warmup)**, explicitly because "in early training, the critic may be poorly aligned with the actor, and applying online RL can degrade the policy."
- **Kill the entropy bonus and tame the noise at the interface.** Entropy coef 0.0–0.0005 in the fine-tuning references above, vs the 0.006–0.01 typical in from-scratch Isaac Lab PPO configs. Also parameterise log-std independently of the state/network (ExT) or freeze std during the first phase — a BC policy trained by MSE has no meaningful std, so RSL-RL's fresh std head starts by injecting exactly the "exploration noise destroys the warm-start" effect described in the mission.
- **DAgger loop with the scripted teacher (cheap, high value):** roll out the current student in Isaac Lab → relabel every visited state with the teacher's IK action → aggregate into the demo set → BC-retrain / continue anchored PPO. This fixes the covariate shift that pure offline BC suffers on a moving conveyor. Machinery already present: **RSL-RL's Distillation algorithm** (Student-Teacher: student acts, teacher provides actions; verified on the rsl_rl repo — 3,097★, 33 releases, "PPO and Student-Teacher Distillation" are its two main-branch algorithms, https://github.com/leggedrobotics/rsl_rl) and **Isaac Lab Mimic** (below).
- **What would be reimplemented vs reused, honestly:** Reuse = RSL-RL PPO + Distillation code, Isaac Lab demo HDF5 pipeline. Reimplement = BC-anchor loss + critic warm-up + β/KL schedule inside RSL-RL's `PPO.update()` (≈100–200 lines), and the DAgger relabelling loop around the existing teacher (≈1 day). No external imitation-RL library survives the Kaggle + Isaac Lab 3.0 + rsl-rl 5 filters intact.

**robomimic** — https://github.com/ARISE-Initiative/robomimic — 1,592★, **MIT**, v0.5.0 (2025-06-20: Diffusion Policy, multi-dataset training, language conditioning); v0.4.0 added robosuite 1.5 + Hugging Face datasets. Isaac Lab itself lists robomimic as a supported framework and even validates `robomimic` as an MIT dependency in its license checks. **Plug-in reality:** Isaac Lab's robomimic path is built around robosuite-style HDF5 and its own BC/BCQ/IQL trainers — it will not train your RSL-RL actor. Value here is (a) a *better BC stage* (BC-RNN / BC-Transformer, sequence modelling instead of frame-wise MSE — plausibly part of why the current BC is fragile), (b) its HDF5 schema and dataset tooling, (c) benchmark hygiene from the CoRL 2021 study (what matters: dataset quality, sequence history, augmentation). Effort to use as a standalone BC trainer on exported HDF5: 2–3 days. Isaac Lab 3.0-specific compatibility of robomimic 0.5 was **not** verified.

**LeRobot (policies)** — https://github.com/huggingface/lerobot — 28,530★, **Apache-2.0**, 11 releases, `pip install lerobot`. Its policy zoo (ACT, Diffusion, VQ-BeT, π0/SmolVLA/GR00T VLAs, HIL-SERL, TDMPC) is oriented to real robots and Gym-style envs (LIBERO/MetaWorld eval). **None of its policies plug into a manager-based Isaac Lab task + RSL-RL runner without writing a new env bridge and abandoning RSL-RL.** Verdict for policies: skip. Verdict for its *dataset format*: integrate (Axis 5).

**Isaac Lab Mimic / `isaaclab_mimic`** — part of https://github.com/isaac-sim/IsaacLab (framework BSD-3; **mimic extension Apache-2.0**; 8,496★; Isaac Lab 3.0.0 targets Isaac Sim 6.2). Verified from official docs: `annotate_demos.py` → `generate_dataset.py` performs MimicGen-style augmentation — parse demos into object-centric subtask segments, transform them to new object poses, stitch and replay — 1,000 generated demos "have been shown to provide good training results" for Stack-Cube; Isaac Lab 2.3 added **SkillGen with cuRobo integration** for motion-planned segment generation. This is DAgger-adjacent data scaling you already own. **Conveyor-specific risk (explicit):** MimicGen-style transformation assumes subtask segments can be re-anchored to a new *static* object pose; a part moving on a belt during the grasp segment violates that assumption unless segments are re-anchored to the object's pose *at segment execution time* or the belt is paused/indexed in the augmented variants. Compatibility of the 2.x-era Mimic scripts with the 3.0 kit-less/OvPhysX flow specifically was **not** verified in the 3.0 docs read — spike it.

**RL library trade-offs vs RSL-RL (the decision is already made by the data):**

**Physics backends:**

- **Newton / MuJoCo-Warp inside Isaac Lab 3.0 — verified from the official 3.0 release notes:** `isaaclab_newton` runs **kit-less (no Isaac Sim)**, supports articulations, rigid objects/collections, contact sensors, MJWarp + XPBD + Featherstone solvers, configurable integrators/contact models, **CUDA-graph support for high-throughput stepping**, and Newton presets for 20+ environments. Isaac Sim 6.2's notes pin the shipped versions at **Newton 1.6.1, MuJoCo/MuJoCo-Warp 3.12.0**. Upstream Newton itself: https://github.com/newton-physics/newton — 5,853★, **Apache-2.0**, Linux Foundation project (Disney Research / Google DeepMind / NVIDIA), 14 releases, pip-installable, and it even ships `basic_conveyor` / `basic_conveyor_forces` examples — directly relevant to belt modelling.
- **The T4 caveat, explicitly:** Newton's current Warp (1.18) requires a Turing GPU (CC 7.5+) **and driver R580+**; on R545–R579 you must pin `warp-lang==1.17.0`. A Kaggle T4 is exactly CC 7.5 (the floor), and **Kaggle's current driver version was not verified** — so a Newton spike must start with a driver/Warp check, and OvPhysX remains the safe default until the A/B is run. Also unverified: whether *this custom conveyor task's* contact behaviour (belt friction, grasp) is equivalent under MJWarp vs OvPhysX — contact models differ (`pyramidal`/`elliptic` vs PhysX), so success rates are not portable between backends. Budget 2–4 days for the A/B including contact re-tuning.
- **ManiSkill3** — https://github.com/haosulab/ManiSkill (org now `mani-skill/ManiSkill`) — 3,470★, code **Apache-2.0**, 37 releases, v3.0.1 (2026-04-21 per comparison source). SAPIEN/PhysX GPU-parallel, heterogeneous scenes, claims 30,000+ FPS RGBD+segmentation collection on an RTX 4090. **⚠️ License trap: ManiSkill's bundled assets are CC BY-NC 4.0 — non-commercial.** As an auxiliary env it would mean re-implementing the conveyor task in a second simulator to cross-check physics/rewards — occasionally worth it, never free. Vulkan rendering setup on Kaggle is an additional unverified risk. Study/spike only.
- **mjlab** — https://github.com/mujocolab/mjlab — 3,279★, **Apache-2.0**, 12 releases, created June 2025 (young). It is literally "the Isaac Lab manager-based API, powered by MuJoCo-Warp," pip/uv-installable with minimal dependencies and a Colab demo — i.e. the most Kaggle-shaped Isaac-Lab-like stack in existence, and RSL-RL lists mjlab as a supported environment library. Its shipped tasks are velocity tracking, motion imitation and a small manipulation set — **no conveyor/pick-place task ships with it**, so this is a port-your-MDP-config spike (2–4 days), valuable mainly as a fast-iteration sandbox if Isaac Lab startup/weight becomes the bottleneck on Kaggle, and as an independent contact-model cross-check.
- **torch.compile / JAX:** No Isaac-Lab-specific speedup evidence was found. The policy is a small MLP and stepping is physics-dominated on a T4; torch.compile's documented failure modes (graph breaks, recompilation, `_orig_mod.` checkpoint-key changes) threaten exactly the BC-checkpoint-loading path this project depends on. JAX enters this stack only via skrl's JAX agents or a full mjlab/MuJoCo-Playground move — neither is a drop-in accelerator for an existing OvPhysX task. **Verdict: skip both as performance projects; revisit only if profiling shows learner time > ~20% of wall-clock.**
- **Rollout/storage optimisations that actually apply on one T4:** keep cameras/rendering **off** during training (render only eval rollouts — see Axis 3 renderer presets); prefer the Newton-Warp renderer or no renderer for any training-time camera need; RSL-RL's rollout storage is already GPU-resident, so the remaining wins are task-side: decimation, contact-sensor scope, and num_envs sized to T4 VRAM rather than copied from 4090 configs. No external project is needed for any of these.

**cuRobo (teacher/collector IK replacement)** — https://github.com/NVlabs/curobo — 1,942★, **Apache-2.0 (V2)**, 12 releases; README verified: *"cuRoboV2 is a significant rewrite and the public API has changed from cuRobo v1 — pin to v0.7.8 if you depend on v1."* V2 (v0.8.0, April 2026) provides GPU-parallel FK/IK, collision checking, trajectory optimisation and ESDF perception in PyTorch/CUDA/Warp, scaling to thousands of parallel problems — i.e. batched IK for *every parallel env's* demo episode at once, vs the current pure-Python DLS loop. **⚠️⚠️ License trap, stated plainly:** cuRobo **V1 = NVIDIA license, non-commercial use only, restriction propagates to derivatives**; **cuMotion (Isaac ROS) = proprietary NVIDIA Isaac ROS license and bundles V1**. And Isaac Lab's own README warns the cuRobo required by `isaaclab_mimic` "has proprietary licensing terms" (`docs/licenses/dependencies/cuRobo-license.txt`). So: integrate **V2 directly**, expect API-porting work (the FANUC proxy needs a cuRobo robot config/YAML + collision spheres; no FANUC config ships upstream — Franka/UR examples do), and expect a **Kaggle build risk**: V1-era install was a ~20-minute source build needing git-lfs as a system package; **whether V2 ships a pip wheel that installs cleanly in a Kaggle kernel was not verified** — this is the first thing to spike, before any API work. Effort if the install works: 3–6 days including validation against the existing DLS teacher (keep the DLS core as the correctness oracle and fallback).

### 3. Rendering / video

Verified from Isaac Lab 3.0 documentation (read 2026-10-28):

- **Renderer system is pluggable in 3.0:** Isaac RTX (needs Isaac Sim), **OVRTX (kit-less, via `isaaclab_ov[ovrtx]`)**, Newton Warp (kit-less, throughput-oriented). The kit-less container image (`nvcr.io/nvidia/isaac-lab:3.0.0-kitless`) ships Newton, OVPhysX, OVRTX and the **`newton_gl`, `newton_rtx`, `viser`, and `rerun` visualizers** — `--viz newton_rtx` selects the OVRTX path tracer, both Newton visualizers "can render offscreen without Isaac Sim."
- **OVRTX quality/cost knobs (official renderer how-to):** OVRTX offers RTX Minimal and photo-real (path-traced) paths; use regular `rgb` "when material appearance, reflections, transparency… matter"; for training cameras use a **`simple_shading_*` preset** instead; `enable_shadows` on RTX Minimal "improve[s] visual faithfulness but cost[s] render time" (path-traced outputs always cast shadows). Practical split for this project: **train with no/simple-shading cameras, produce hero video in a separate eval pass with OVRTX photoreal + shadows** — on a T4 (which has RT cores but is far below the RTX 4080/16 GB class NVIDIA lists for full Isaac Sim), expect path-traced video to be an offline, small-batch job, not a training side-effect. Known issue in 3.0 docs: RTX renderers can produce blank first frames while materials load (warm up with ~12 `sim.render()` calls before recording).
- **Newton Warp renderer** is explicitly the throughput choice (shadows/textures/ambient via `NewtonWarpRendererCfg`); it will not match OVRTX path tracing for industrial hero shots. Use it for debugging video, OVRTX for deliverable video.
- **Viser** — https://github.com/nerfstudio-project/viser — 2,836★, **Apache-2.0**, 108 releases, `pip install viser`, web-based 3D viewer with programmatic camera control — and it is **already an Isaac Lab 3.0 visualizer**, as is **Rerun** (https://github.com/rerun-io/rerun — 11,653★, **dual MIT/Apache-2.0**, 91 releases, `pip install rerun-sdk`). Since Rerun is already integrated for rollout logging, no new visualisation dependency is justified; use Viser where a shareable web view / scripted camera path is easier than Rerun, and drive OVRTX camera sensors for actual mp4 output. Neither Viser nor Rerun raises *rendered* quality — they are viewers/loggers, not renderers. Conflating them with OVRTX is the main trap in this axis.
- **Assets — the big find: NVIDIA SimReady Central Library** (announced 21 Oct 2026, Hugging Face / NVIDIA): **2,000+ free, ungated, simulation-ready OpenUSD assets** with collision geometry, mass and friction metadata; contributing OEMs include **FANUC**, Universal Robots, Franka, Robotiq, Comau. Status: **research preview**. **⚠️ Per-asset license terms were not verified** (the library is described as "free"; that is not a license) — treat as integrate-for-research, verify before commercial redistribution. This is the first place to look for a real FANUC-arm / conveyor / racking model instead of dressing primitives.
- **Assets — CC0 materials (safe):** **Poly Haven** and **ambientCG** publish PBR materials/HDRIs under **CC0** (ambientCG: 2,000+ materials, up to 8K, no attribution). These are texture sets, not USD: budget 1–2 days to convert a small industrial set (belt rubber, brushed/painted steel, safety-yellow paint, concrete floor, cardboard) into USD/MDL materials that OVRTX will shade well. This, plus real HDRI lighting, is the cheapest large jump in "industrial-quality" appearance.
- **⚠️ Asset traps:** ManiSkill assets **CC BY-NC 4.0** (non-commercial) — do not lift ManiSkill scene assets into deliverable video. Kenney's industrial/conveyor kit is CC0 but low-poly game-styled — fine for placeholders, wrong for hero renders. Isaac Lab assets not explicitly listed in its `docs/licenses` fall under the **Isaac Sim license** per the Isaac Lab README — another reason to prefer SimReady/CC0 assets you can document.

### 4. Manipulation benchmarks / task design (specific elements worth borrowing)

No public suite found ships a *moving-conveyor* pick-and-place task — Factory, IndustReal, ManiSkill and Isaac Lab tasks are static-scene. The borrowable value is in reward staging, success definitions and curricula:

- **Isaac Lab upstream Lift / Stack (Franka) — borrow the staging verbatim:**
  - Reaching: `1 − tanh(distance / 0.1)` — bounded, smooth, always-on.
  - Grasped (binary): end-effector within **0.04 m** of the object **AND** gripper fingers closed past threshold.
  - Lifted (binary, weight 1.5): object z above a minimal height.
  - **Goal-distance reward is gated on `lifted`** — the object-to-goal term is multiplied by the lifted condition, so the policy cannot earn placement reward by sliding/dragging. This staged gating is the single most transferable idea for conveyor pick→place (gate "carry/place" terms on a verified grasp; gate "place" terms on the object being off the belt).
  - Regularisation: action-rate and joint-velocity L2 penalties throughout; Stack uses a 5-stage curriculum of reward terms.
- **ManiSkill PickCube / StackCube — borrow the success definitions:** PickCube success = cube within **2.5 cm of goal AND the robot is static**; StackCube success = top cube **stably placed AND not grasped**. For a conveyor cell, adopt: success requires the part *released* (not grasped), *settled* in the target bin/zone for N consecutive steps, with the arm clear — this kills "holding it over the bin at timeout" false successes, which matter when success is currently 0% and every signal will be scrutinised.
- **IndustReal (Factory successor, arXiv:2305.17110, Table VI) — borrow curriculum-scaled rewards:** per-step keypoint-distance reward; SDF-based alignment reward `−log(mean φ(xᵢ))` (×10) for insertion-class precision; interpenetration penalty `1 − tanh(d/ε_d)`; and critically, **reward terms scaled by (current randomisation range / max) and (current curriculum difficulty / max)**, with a sparse **success bonus of 10.0**. Mapped to this cell: belt speed, part spacing and part-pose randomisation become the curriculum axes, and the reward scale grows with them — a principled way to start at belt-speed 0 (where the teacher demos live) and earn your way to full speed.
- **Factory (arXiv:2205.03532) — borrow the contact approach and an observation warning:** Factory's contribution is SDF-based contact that stays stable and fast for tight-clearance, contact-rich interaction (1–1.5 h to train 4 policies on 1 GPU in Isaac Gym). Its observation ablation is a direct caution for this project: pose-only was *fastest* to success, pose+velocity had the best success, and **adding force and action observations dropped success from 0.78 to 0.33** — do not add contact-force observations "because industrial" without an ablation.
- **robosuite / robomimic tasks (PickPlace, Can, Square):** useful as *reference task decomposition* (reach → grasp → lift → transport → place into a receptacle, with per-stage checks) and because IBRL/RLPD results are reported on exactly PickPlaceCan — if you ever run the off-policy spike (skrl SAC), these are the comparison tasks whose published numbers tell you whether your demo count is in a sane range (IBRL reports large gains at **10 demos / 100k interactions** on PickPlaceCan).

### 5. Data / experiment infra

- **Demo format decision:** You have two defensible targets, and they serve different futures.
  - **robomimic / Isaac Lab HDF5 — zero-friction today.** Isaac Lab Mimic already reads/writes `dataset.hdf5`; robomimic's trainers consume the same family of HDF5. Keeping demos in HDF5 costs nothing and keeps Mimic augmentation available.
  - **LeRobotDataset v3 — the portable future.** Verified from the LeRobot repo: synchronised **MP4 video + Parquet state/action**, episode metadata, Hub hosting/streaming, dataset surgery tools (delete/split/merge episodes, add/remove features); `pip install lerobot` (base install is lightweight; use the `[dataset]` extra and *not* the training stack). Writing an HDF5→LeRobot exporter is 1–2 days and buys: Rerun-native visualisation (Rerun ingests LeRobot format), compatibility with every current VLA/BC trainer, and a publishable artifact. **⚠️ License trap for *imported* data:** an Oct 2026 audit of the 3,000 most-downloaded LeRobot Hub datasets found 56.5% carry an unedited default `apache-2.0` template tag and ~200 datasets traceable to a known source declare a *different* license than that source — the Hub tag does not grant rights. Irrelevant for your own teacher demos; critical if you ever train on someone else's Hub dataset.
- **Experiment tracking that works offline in Kaggle:**
  - **First choice: what RSL-RL already supports.** rsl-rl-lib's documented loggers are TensorBoard, Weights & Biases and Neptune. **W&B offline mode is the Kaggle-proven pattern**: set `WANDB_MODE=offline` *before* import, logs land in the kernel output, `wandb sync` afterwards (a dedicated `kaggle-wandb-sync` tool exists on PyPI for exactly this push→poll→download→sync loop). Cost: ~0 days. W&B's hosted service is a commercial product — the offline files are yours, but do not treat the cloud tier as open source.
  - **MLflow** — Apache-2.0, 20k+★, local file store (`./mlruns`) works fully offline and `pip install mlflow` is the whole setup. Heavier than needed here, and reviews report the UI struggling past ~1,000–3,000 metrics per run; only adopt if you want its model-registry discipline. 0.5–1 day.
  - **Aim** — Apache-2.0, ~6.3k★, self-hosted and offline-friendly, **but** GitHub-API-derived data (Oct 2026) shows ~1 commit in the last 12 months — maintenance risk. Skip.
  - **TensorBoard alone** remains the zero-risk floor: it is already the RSL-RL default, files survive Kaggle session death in the output directory, and it pairs with Rerun `.rrd` files for the visual side.

## Notable Rejects

| Project / idea | Reason |
|---|---|
| **Stable-Baselines3** as the RL library | ~30× slower than RSL-RL on Isaac Lab's own GPU-vectorised benchmark (6,320 s vs 207 s); no vectorised training in Isaac Lab's comparison. Maturity (13,940★, MIT) does not compensate. |
| **RLPD repo as a library** (`ikostrikov/rlpd`) | JAX + D4RL, 0 releases, SAC-family — architecturally incompatible with an on-policy PPO pipeline. Its *sampling/normalisation recipe* is harvested via skrl SAC (Rank 6) if needed. |
| **IBRL repo as code** | TD3/MuJoCo-2.1/C++-compile stack, 80★, and **no license file** — copying it is both impractical and legally unsafe. Algorithm studied, code not taken. |
| **LeRobot policies / trainers** | Real-robot/Gym-env oriented; adopting them means abandoning the manager-based task + RSL-RL runner for no demonstrated gain on a state-based industrial task. (Dataset format kept — Rank 5.) |
| **CleanRL as a library** | By its own README it is "not a modular library and not meant to be imported." Keep as a PPO reference read only. |
| **Genesis World** | Apache-2.0 and popular, but in the sources checked there is **no published, like-for-like throughput or manipulation-task evidence vs Isaac Lab**, and it would be a third task definition. No conveyor/manipulation suite advantage over ManiSkill/mjlab for this purpose. |
| **torch.compile / JAX rewrites for speed** | No Isaac-Lab evidence; physics-bound on T4; compile's checkpoint-key side effects endanger the BC warm-start path that is already the project's weakest point. |
| **Aim (experiment tracking)** | Apache-2.0 but ~1 commit in 12 months (GitHub-API-derived, Oct 2026) — do not build infra on it. |
| **cuRobo V1 / cuMotion / Isaac Lab Mimic's pinned cuRobo** | **Non-commercial / proprietary NVIDIA terms.** Only cuRobo V2 (Apache-2.0) is acceptable, integrated directly. |
| **ManiSkill / SimReady assets in deliverable video** | ManiSkill assets are **CC BY-NC**; SimReady per-asset terms are unverified. Neither may be assumed cleared for commercial output. |
| **FLaRe as an integration** | A fine-tuning *framework for VLA-scale BC policies*; no verified maintained repo fits a small MLP PPO actor. Its stabilisation ideas are already folded into Rank 1. |

## Could not verify / open questions

- **Kaggle T4 driver version vs Warp 1.18's R580+ requirement** — determines whether Newton (Rank 4) works at all or needs `warp-lang==1.17.0`. Check `nvidia-smi` in-kernel first.
- **cuRobo V2 install on Kaggle** — whether a pip wheel installs without system packages / long CUDA source builds in a kernel session. This gates Rank 3.
- **Isaac Lab Mimic scripts under the 3.0 kit-less / OvPhysX flow** — docs read were substantially 2.x-era; 3.0 compatibility is plausible (Mimic is still in-tree) but not confirmed, and the moving-belt objection (Rank 2) is untested in any source.
- **Exact Isaac Lab 3.0 / rsl-rl-lib 5.x compatibility of robomimic 0.5 and skrl's current release** — both are Isaac-Lab-supported frameworks in principle; neither's current release notes were verified against Lab 3.0.0 specifically.
- **SimReady Central per-asset licenses** and whether a FANUC M-10iD-class model specifically (vs FANUC as a contributing OEM generally) is in the library.
- **Latest release dates** for skrl, RLPD (none), SB3's current line, and rsl-rl-lib 5.0.1's publication date were not captured; maturity claims above rest on release counts, commit activity and the versions' existence, not on those dates.
- **No public moving-conveyor pick-and-place benchmark was found** in Factory, IndustReal, ManiSkill, robosuite or Isaac Lab upstream — the conveyor curriculum in Findings §4 is a synthesis, not a citation.
- Whether the current 0% success is *primarily* the BC→RL interface vs reward/task design cannot be decided from external sources; Ranks 1, 7 and 10 are sequenced to discriminate between those hypotheses cheaply.
